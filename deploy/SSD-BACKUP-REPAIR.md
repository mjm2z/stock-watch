# StockWatch backup verification on SSD

The November 5 recovery attempt copied the primary export in 43 minutes, then exceeded the 130-minute service limit during HDD verification. A restored older export passed full integrity/reopen checks on a1990 SSD in 60 seconds. This backup-only repair leaves application logic and the overall service timeout unchanged.

`STOCK_WATCH_BACKUP_SSD_CONFIG` enables verification of the closed export through a dedicated SSH identity. The receiver's forced command accepts only a run ID, size and checksum, stages under its own private directory, shares Home Ops' SSD lock, requires 20 GiB reserve, and removes its temporary export afterward. It performs full SQLite integrity checking and an independent application-table reopen, including auxiliary datasets. The sender validates the receipt's run ID, size, checksum, status and method, then rehashes the local export before publication. Receipts are adjacent to finalized exports; a receipt without its matching database is not recovery evidence.

Stage limits: producer copy 60 minutes; each hash pass 10 minutes; SSD transfer 45 minutes; integrity/reopen 10 minutes. The existing per-database two-hour budget and service-wide 130-minute ceiling still apply, so stage maxima cannot all be consumed. Journal events report phase, elapsed time, and transfer bytes. No fallback silently accepts an unverified export. History preservation remains enabled.

`install-ssd-backup.py --check` checks the installed release/module hashes, existing history-preservation drop-in, candidate manifest, and configuration without modifying the service. `sudo python3 install-ssd-backup.py --queue` copies the checked payload to root-owned staging and waits up to 170 minutes for idle jobs, available memory, low I/O pressure, and the shared source-disk lock. It installs only backup modules/credentials and one drop-in, saves rollback evidence, and starts the existing unit. It does not stop competing jobs. The operator supplies sudo locally; do not send passwords to the agent.

Rollback: `sudo python3 install-ssd-backup.py --rollback /var/backups/stock-watch-ssd-repair/TIMESTAMP`. It refuses an active backup or subsequent edits, restores previous modules, and removes only recorded added configuration. It does not alter backup history or restart jobs. The separately installed SSD forced-command key/receiver can remain dormant; their authorized_keys rollback copy is retained on a1990.

Validation: worker suite and backup deployment tests; real restricted-SSH fixture transfer before production installation. A queued start is not acceptance: require a fresh finalized primary and auxiliary export, producer success, and fresh Toshiba/MyCloud recovery tests. Database freshness derives from export capture time, not replica time. Off-machine auxiliary coverage remains a separate outstanding gap.
